# 11 · 用 Spec Coding 方式复建

本目录不是一份笼统的产品介绍。每个阶段都是一个可执行的工程 spec：先定义**能观察到的结果**，再约定接口和文件边界，把实现拆成小任务，最后用测试、API 响应和运行事件证明完成。建议始终使用同一套 ID，把“需求—设计—任务—证据”串起来。

## 每阶段的四份输出

| 层次 | 编码 Agent 应交付的内容 | 不能只交付 |
| --- | --- | --- |
| Requirements | 功能行为、边界和失败时的结果；每条有稳定 ID | “支持 MCP”“支持会话”这样的口号 |
| Design | 模块归属、输入输出、磁盘格式、SDK 映射、权限与数据流 | 只有页面草图，没有后端契约 |
| Tasks | 按依赖顺序的文件修改、迁移、测试夹具和运行命令 | 一次性大改且无法定位失败步骤 |
| Verification | 每条需求对应测试／手工任务、预期与实际结果、平台与版本 | 只说“已测试”或“应该能运行” |

一条示例追踪链：`RUN-03 新会话固定配置` → `Conversation.config` 与 `server/conversations.ts` → 先创建会话快照再启动 SDK → 修改 Agent 后读取旧会话仍保留原模型和规则。需求 ID 不属于运行时数据；它只帮助复建者审查交付。

## 每一轮怎样使用文档

1. **读 spec**：向编码 Agent 发送本目录 [总提示词](README.md) 和目标阶段文档；要求先列出需求 ID、已有实现和缺口。不要从私人聊天复制密钥或原始运行日志。
2. **定设计**：让它给出文件树、API 请求／响应、持久化形状和异常状态。对已有契约只做兼容扩展；如果需要改格式，先写迁移和回退办法。
3. **拆任务**：按“共享类型 → 存储与后端 → API → 前端 → 测试 → 文档”排序。每完成一个任务就能通过类型检查或一个明确测试，不把所有失败积到最后。
4. **实现和验证**：按该章“实现步骤”执行；每一步记录改动文件、运行命令和结果。需要真实 Qoder、浏览器、Apify 或百炼时，单独记录实际联网验证，不能用 mock 冒充。
5. **阶段封版**：该章的验收矩阵全部通过，逐文件索引能解释新增文件，下一章的前置条件成立；再继续下一阶段。

## 给编码 Agent 的阶段开工模板

> 请阅读总提示词、01 架构契约和当前阶段 spec。先只输出：需求 ID 清单、当前代码与目标的差距、拟新增／修改的文件及其职责、API 和磁盘格式、失败与恢复路径、按依赖排序的任务清单、每条需求对应的验证方法。随后直接实施这些任务。每完成一个任务运行最小可行检查；阶段结束执行 spec 的完整验收，并逐项报告“通过／失败／未实测”。不得把测试环境中的模拟服务结果写成真实外部服务结果。

## 给编码 Agent 的阶段收尾模板

> 请依据本阶段每条需求 ID 审核代码和测试。逐条给出实现文件、验证命令或 API 操作、预期结果和实际结果；指出未覆盖的边界。检查是否泄漏凭据、是否改变上一阶段数据契约、是否需要更新文件索引与快速指南。发现缺口就修复并重测；全部通过后再交付下一阶段。

## 复建的边界

“忠实复建”指行为和架构边界相同，不要求每段源码完全一致。演示版 34 条历史和 4 个媒体文件是已生成数据，复建者可以自行制作安全夹具。自动记忆写入、跨平台运行和付费外部服务调用必须以真实测试证据描述；无证据时保持“未验证”。
